# AI 幻觉抑制方案

## 1. 背景

随着系统逐步承接配置查询、日志分析、运维问答和 SOP 辅助生成，用户会天然把回答当成“可执行事实”而不是“语言生成结果”。

如果系统在依据不足时仍输出完整结论，就容易出现以下问题：

- 编造用户名、角色、权限关系
- 编造云资源、实例、时间范围、错误码
- 把推断说成事实
- 在没有足够证据时给出过度确定的操作建议

因此，AI 幻觉抑制应作为产品级目标推进，而不是只在 Prompt 层面零散修补。

## 2. 总体目标

总体目标：抑制 AI 幻觉。

具体要求：

1. 有依据时再给确定性结论
2. 无依据时明确说明依据不足
3. 高风险回答默认保守，不补全不存在的细节
4. 用户可以看到回答依据或知道当前为什么不能确认
5. 幻觉问题可以被记录、复盘和持续收敛

## 3. 适用范围

本方案优先覆盖以下场景：

- 用户、角色、权限、认证方式相关问答
- 配置项解释、配置排障、配置变更建议
- 云资源、日志、审计、故障根因分析
- SOP 推荐、运维步骤建议、修复路径建议

以下内容属于高风险场景，应优先严格约束：

- 权限判断
- 安全结论
- 生产运维建议
- 审计和根因归因

## 4. 核心原则

### 4.1 有据再答

回答应尽量绑定实际依据，例如：

- 配置文件
- 已授权的数据源
- 检索命中的文档
- 日志查询结果
- 用户当前上下文中明确给出的信息

### 4.2 无据不补

当系统无法确认事实时，应直接说明：

- 当前没有足够依据支持该结论
- 需要补充时间范围、环境、数据源或对象标识
- 当前回答只能提供排查思路，不能确认最终结论

### 4.3 高风险默认保守

对于权限、配置、运维、审计类高风险问题：

- 不编造账号、角色、资源 ID、时间、错误码
- 不把猜测包装成结论
- 不省略前提条件和限制说明

### 4.4 区分事实、推断、建议

输出应尽量区分三类信息：

- 事实：当前有明确依据支撑
- 推断：基于现有信息做出的合理判断
- 建议：下一步可执行动作或补充信息项

## 5. 落地策略

### 5.1 Prompt 与回答约束

系统提示词至少应明确以下规则：

- 不允许编造用户、角色、邮箱、部门、资源、日志字段、配置项
- 依据不足时优先返回“不确定”或“需要补充信息”
- 高风险问题优先给出依据和限制，而不是直接给结论
- 未在上下文中出现的字段名、地址、回调参数、开关名不得擅自补全

### 5.2 检索与上下文约束

检索链路应满足以下要求：

- 只使用当前用户被允许访问的数据源
- 召回结果为空时，显式进入降级分支
- 召回结果与问题弱相关时，不强行组织确定性答案
- 尽量保留来源元数据，例如文档名、日志来源、时间范围

### 5.3 输出结构约束

回答结构建议至少包含以下语义：

- 当前结论
- 依据来源
- 不确定性说明
- 下一步建议

如果当前做不到结构化输出，至少要保证高风险场景中能明确写出：

- “依据是什么”
- “哪些部分无法确认”
- “建议补什么信息”

### 5.4 前端交互约束

前端建议补充以下能力：

- 展示回答依据或来源摘要
- 在无依据时展示“依据不足”提示
- 对高风险建议增加醒目的限制说明
- 为用户提供“这条回答不可信”反馈入口

### 5.5 审计与复盘

建议记录以下信息用于复盘：

- 用户问题
- 使用的数据源或检索命中情况
- 最终回答
- 是否带来源
- 是否被用户标记为不可信

## 6. 验收标准

第一阶段至少满足以下标准：

1. 检索为空时，不再输出看似完整的确定性结论
2. 高风险问题不再编造账号、角色、资源、时间和配置字段
3. 回答中可以识别出“事实”和“推断”的边界
4. 前端能展示“有依据”或“依据不足”的状态
5. 幻觉样本可以被收集并进入后续迭代

## 7. 与当前计划的关系

该方案与“用户导入、IDaaS 接入”计划并不冲突，反而互相支撑：

- `IDaaS / OIDC` 接入可以减少身份和权限来源不清带来的误答
- `builtin` 导入边界清晰后，可以减少系统对本地用户模型的错误猜测
- 幻觉抑制规则可以作为后续 Prompt、检索、前端提示和审计的统一基线

## 8. 文档归档约束

本项目与 AI 幻觉抑制相关的文字文档统一放在 `docs/` 目录，例如：

- 方案说明
- 设计文档
- 验收标准
- 复盘结论

模板文件、静态资源和可下载产物可根据类型放在其他目录，但对应说明文档应在 `docs/` 中保留入口。
