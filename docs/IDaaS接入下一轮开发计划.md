# IDaaS 接入下一轮开发计划

## 1. 目的

当前版本已经完成阿里云 IDaaS 的 OIDC 登录主链路，测试环境可通过“使用 IDaaS 登录”进入系统。下一轮开发不再以“能否登录”为重点，而是把认证体系收口到可持续维护、可灰度上线、可运维排障的状态。

本计划用于明确下一轮工作的范围、顺序和验收标准，避免在主链路已通的情况下继续零散加需求。

## 2. 当前基线

截至当前版本，已经具备以下能力：

- `OIDC / IDaaS` 配置模型已接入统一配置
- 后端已支持 `/api/auth/oidc/login` 与 `/api/auth/oidc/callback`
- 登录页已支持根据 `auth.methods` 自动展示 IDaaS 登录入口
- `admin-ui` 已支持维护 `OIDC / IDaaS` 配置
- `builtin` 用户导入模板、导入接口和导入反馈已打通
- 选择数字员工页、会话页和账户区的基础样式已完成一轮修正

当前仍存在以下缺口：

- OIDC 登出链路尚未完整闭环
- 目前主要依赖 `id_token` 取用户信息，尚未补 `userinfo` 兜底
- `builtin` 仍保存在 `config.yaml`，尚未迁移到 `SQLite`
- 登录/退出审计能力不足
- IDaaS 上线文档、联调清单、异常排查文档尚未独立沉淀

## 3. 总体目标

下一轮目标统一收敛为四件事：

1. 把 `OIDC / IDaaS` 做成可上线的正式认证能力
2. 把 `builtin` 从配置文件迁移到 `SQLite`
3. 把认证相关的排障、联调、配置说明沉淀为运维文档
4. 为后续权限映射、审计和 AI 幻觉抑制提供更稳定的身份基础

## 4. 非目标

下一轮不做以下事项：

- 一次性支持 `LDAP`
- 引入 `MySQL / Postgres`
- 重做整套用户管理后台
- 完整的本地密码找回和密码生命周期体系
- 一次性做完所有审计报表页面

## 5. 开发顺序

### 5.1 第一阶段：OIDC 收口

目标：让 IDaaS 登录具备完整闭环，而不是只完成登录成功路径。

建议交付物：

- `/api/auth/oidc/logout`
- 前端退出逻辑支持本地退出与 IDaaS 退出联动
- 登录失败页、回调失败页、配置错误提示优化
- 角色映射规则联调验证
- 一份测试环境联调检查清单

建议实现：

1. 本地退出后清理项目 JWT、用户态和前端缓存
2. 若 Provider 支持退出端点，追加跳转到 IDaaS 退出地址
3. 明确“仅退出本地会话”和“同时退出 IDaaS 主登录态”的行为边界
4. 增加典型错误场景提示：
   - `redirect_uri` 不匹配
   - `client_id` 配置错误
   - `issuer` 不可达
   - `state / nonce` 失效
   - `claim` 缺失
5. 补一轮接口级测试，覆盖退出和异常分支

验收标准：

- 用户可从系统内完成退出，并回到明确的登录态页面
- OIDC 配错时，页面能给出足够明确的提示，不再只有笼统报错
- 角色映射命中与未命中时，系统行为可预期

### 5.2 第二阶段：用户信息与 Claim 兼容性增强

目标：降低不同 IDaaS / OIDC Provider 在 claim 结构差异上的接入摩擦。

建议交付物：

- `userinfo` fallback 能力
- 更稳健的用户名、邮箱、显示名、组信息回退策略
- 一组可配置的 claim 优先级规则

建议实现：

1. 继续以 `id_token` 为第一优先级
2. 当关键字段缺失时，使用 `access_token` 调用 `userinfo`
3. 对 `username / email / displayName / groups` 建立统一解析函数
4. 在日志中记录“命中的是哪条 claim 解析路径”，便于联调排查
5. 对阿里云 IDaaS 的实际字段命名补一份适配说明

验收标准：

- 同一套代码可以兼容“claim 在 `id_token`”与“claim 在 `userinfo`”两类场景
- 用户名、邮箱、显示名缺失时，系统有明确回退逻辑，不出现空白账户展示

### 5.3 第三阶段：builtin SQLite 化

目标：将兜底本地账号从配置文件迁移到 `SQLite`，正式落地方案 B：`OIDC + SQLite builtin`。

建议交付物：

- `SQLite builtin` 仓储层
- `builtin_users / builtin_roles / builtin_user_roles` 表结构
- 从 YAML 到 `SQLite` 的迁移入口
- `xlsx` 导入改为写入 `SQLite`
- 本地账号启用状态、最近登录时间等基础字段

建议实现：

1. 优先保持现有 `builtin` Provider 接口不大改，通过仓储层切换底层实现
2. 保留 YAML 到 `SQLite` 的一次性迁移能力
3. 导入逻辑改为面向仓储接口，而不是直接回写配置文件
4. 继续保留少量本地管理员账号作为 IDaaS 故障兜底
5. 配置文件中只保留数据库路径、认证方式、JWT 和 OIDC 相关配置

验收标准：

- `builtin` 账号与角色不再长期保存在 `config.yaml`
- 导入、登录、角色校验在 `SQLite` 存储下行为一致
- OIDC 异常时仍可通过本地管理员账号进入系统

### 5.4 第四阶段：审计与运维文档收口

目标：让认证体系具备上线后的基本可观测性和可运维性。

建议交付物：

- 登录成功/失败审计日志
- 退出审计日志
- 测试环境部署与联调说明
- 生产环境切换检查清单
- 常见错误排查文档

建议实现：

1. 记录登录来源、认证方式、用户名、时间、结果和错误摘要
2. 区分 `builtin` 登录与 `oidc` 登录
3. 为 `redirectURL`、域名、反向代理头、HTTPS 切换提供文档模板
4. 单独沉淀 IDaaS 联调 FAQ，避免问题只存在聊天记录里

验收标准：

- 联调和上线问题可以通过文档快速定位，而不需要重新翻代码
- 登录失败至少能从日志定位到“配置问题、回调问题、claim 问题”中的哪一类

## 6. 推荐排期

建议按以下顺序推进：

1. `OIDC logout + 错误提示优化`
2. `userinfo fallback + claim 兼容`
3. `SQLite builtin`
4. `审计日志 + 运维文档`

原因：

- 第一阶段最直接影响测试和上线体验
- 第二阶段最直接影响不同租户和不同账号的兼容性
- 第三阶段是目标架构收口，但不应该阻塞 OIDC 的运维闭环
- 第四阶段适合在主功能稳定后集中补齐

## 7. 风险与注意事项

### 7.1 OIDC 退出风险

- 如果只清本地 JWT，不退出 IDaaS 主登录态，用户会误以为已经完全退出
- 如果强制退出 IDaaS，又可能影响同浏览器下的其他企业应用

因此退出能力需要明确区分：

- 系统本地退出
- 联动 IDaaS 全局退出

### 7.2 Claim 差异风险

- 不同 Provider 的用户名、邮箱、组字段命名差异很大
- 不能默认 `preferred_username / email / groups` 一定存在

因此必须保留：

- 可配置 claim 名
- `userinfo` fallback
- 缺失时的明确降级提示

### 7.3 SQLite 迁移风险

- 若直接切换存储层，可能影响现有本地管理员登录
- 若迁移过程没有兜底策略，容易把应急账号一起迁坏

因此需要保留：

- 迁移前备份
- 迁移结果校验
- 至少一个可确认可登录的本地管理员账号

## 8. 文档输出要求

下一轮新增或更新的认证相关文档统一放在 `docs/` 目录下，建议至少补齐：

1. `docs/IDaaS联调与排障手册.md`
2. `docs/SQLite builtin 迁移设计.md`
3. `docs/认证审计与日志说明.md`

## 9. 本轮结论

当前版本已经完成“IDaaS 能登录”的目标，下一轮应正式进入“IDaaS 能上线、能退出、能排障、builtin 能收口到 SQLite”的阶段。

因此，下一轮开发建议以 `OIDC 收口` 为起点，以 `OIDC + SQLite builtin` 为最终结构，不再围绕 YAML 本地账号做长期扩展。
