# 用户导入、IDaaS 接入与 AI 幻觉抑制计划

## 1. 背景

当前系统的登录能力仍以本地内置账号为主，适合小规模管理员使用，但不适合人数持续增长的业务场景。现阶段已经出现三个明确诉求：

1. 需要支持批量导入用户，降低人工逐个录入成本。
2. 对话使用人数上来后，忘记密码和重置密码会变成高频运维问题。
3. 随着问答范围扩大，需要主动抑制 AI 幻觉，避免系统在依据不足时编造用户、权限、资源、时间和操作结论。

同时，团队已经在使用阿里云 IDaaS，因此后续认证体系应优先考虑与现有企业身份系统打通，而不是继续围绕本地密码体系做大量长期建设。

本计划用于明确三项工作的边界与优先级：

1. `builtin` 内置用户的 `xlsx` 模板与导入能力
2. 阿里云 IDaaS 作为主认证源的接入方案
3. 问答链路中的 AI 幻觉抑制目标与落地边界

## 2. 当前现状

### 2.1 已有能力

- 系统已支持 `builtin` 本地用户名密码登录
- `builtin` 当前仍保存在 `config.yaml` 的 `auth.builtinUsers / auth.roles`
- 配置模型已经预留 `ldap` 和 `oidc` 字段
- 后端认证中间件已经统一使用项目自己的 JWT

### 2.2 当前缺口

- 运行时尚未实现 `LDAP` 和 `OIDC` Provider
- 登录接口目前只支持用户名密码登录
- 前端登录页目前只有账号密码表单
- 配置管理 UI 目前只支持本地用户和 JWT 参数维护
- 系统“初始化完成”判断目前默认要求至少存在一个本地用户
- `builtin` 用户存储尚未 SQLite 化
- 当前问答链路缺少“证据绑定、未命中降级、高风险场景保守回答”的统一约束

### 2.3 现阶段判断

- `xlsx` 导入可以解决“批量建人”问题
- 但无法解决“忘记密码、密码策略、账号生命周期管理”问题
- 长期正确方向应是：`IDaaS` 做主认证，`builtin` 仅保留少量兜底管理员账号
- AI 幻觉问题不能只靠 Prompt 兜底，需要把数据依据、前端提示和运行时约束一起设计

## 3. 总体策略

后续认证与用户体系建议采用“双轨制”：

1. `IDaaS / OIDC` 作为主认证方式，承接日常用户登录
2. `builtin` 保留为应急登录和本地管理员兜底能力，并逐步迁移到 `SQLite`

同时，问答链路应采用“有据再答、无据说明”的收敛策略：

1. 能从配置、知识库、日志或检索结果中拿到依据时，再输出确定性结论
2. 依据不足时，明确说明“不确定”或“需要补充信息”，而不是补全细节
3. 对权限、配置、运维操作、审计结论类高风险问题，优先给出来源和边界说明

不建议继续把主要精力投入到本地密码体系扩展上，例如：

- 找回密码
- 修改密码流程
- 密码复杂度策略
- 密码过期策略
- 批量重置密码

这些能力 IDaaS 天然更适合承接。

## 4. 目标与非目标

### 4.1 目标

本轮计划目标如下：

1. 提供一个可直接给运营或管理员使用的 `xlsx` 用户导入模板
2. 增加 `builtin` 用户批量导入能力
3. 将 `builtin` 本地账号与角色迁移到 `SQLite`
4. 设计并实现基于阿里云 IDaaS 的 OIDC 登录方案
5. 保持现有项目 JWT 和权限中间件尽量不被推翻
6. 为后续角色映射和单点登录扩展留出结构空间
7. 建立 AI 幻觉抑制基线，确保系统在依据不足时优先降级而不是编造

### 4.2 非目标

以下事项不作为第一阶段目标：

- 完整的本地密码找回能力
- 完整的用户管理后台重构
- 一次性支持所有第三方身份源
- 一次性做完 LDAP 和 OIDC 两套认证
- 引入独立的外部数据库服务（如 MySQL / Postgres）
- 第一阶段把 AI 幻觉完全消除

## 5. 推荐方案

### 5.1 用户导入

`xlsx` 导入只服务于 `builtin` 本地账号，不与 IDaaS 用户混用。

长期目标上，`builtin` 用户应落到 `SQLite`，而不是继续长期保存在 `config.yaml` 中。

但考虑到当前项目仍处于接入和收口阶段，第一步可以先把模板、校验、导入入口和角色整理链路做通，作为过渡基线；后续再把存储层从 `auth.builtinUsers / auth.roles` 迁移到 `SQLite`。

推荐第一版模板只包含当前系统真实能承载的字段，避免模板先膨胀、系统后补能力：

`Sheet: users`

| 列名 | 必填 | 说明 |
| --- | --- | --- |
| `username` | 是 | 用户名，需唯一 |
| `initial_password` | 是 | 初始明文密码，导入时由服务端按现有规则生成哈希 |
| `roles` | 否 | 多个角色用英文逗号分隔，例如 `admin,user` |

示例：

```text
username,initial_password,roles
admin.local,Strong@123456,admin
zhangsan,Temp@123456,user
lisi,Temp@123456,"user,ops"
```

第一版不建议加入以下字段：

- 显示名
- 邮箱
- 手机号
- 部门
- 启用/禁用状态

原因是当前本地用户模型本身并不承载这些字段，模板先加只会制造“看起来支持、实际没有落地”的错觉。

### 5.2 IDaaS 接入

推荐使用 **OIDC 授权码模式** 接入阿里云 IDaaS。

整体思路：

1. 前端点击“使用 IDaaS 登录”
2. 浏览器跳转到后端 `/api/auth/oidc/login`
3. 后端重定向到 IDaaS 授权页
4. IDaaS 回调 `/api/auth/oidc/callback`
5. 后端校验 `state`、`nonce`、`issuer`、`id_token`
6. 后端从 `claim` 中提取用户名、邮箱、角色信息
7. 后端继续签发本项目自己的 JWT
8. 前端沿用现有本地 JWT 机制访问业务接口

该方案的优点：

- 与现有鉴权中间件兼容度高
- 不需要把 IDaaS 的 token 直接暴露给前端业务层
- 后续切换其他标准 OIDC Provider 时复用性更好

### 5.3 AI 幻觉抑制

AI 幻觉抑制不应只理解为“改一句 Prompt”，而应作为回答链路的默认约束。

建议第一版遵循以下原则：

1. 回答必须尽量绑定到实际依据，例如配置、日志、知识文档、检索命中结果
2. 未检索到依据时，优先返回“当前没有足够依据支持该结论”
3. 不允许编造以下信息：
   - 用户名、角色、部门、邮箱
   - 云资源 ID、实例名、日志时间、错误码
   - 未在配置中出现的字段、开关、地址、回调参数
4. 对高风险输出显式区分：
   - 已确认事实
   - 基于现有信息的推断
   - 建议用户补充的条件
5. 前端应给出“回答依据”或“依据不足”的可见提示，避免用户把推断当事实

## 6. 分阶段计划

### 阶段一：模板与导入基线

目标：先解决本地账号批量初始化问题。

交付物：

- `xlsx` 模板文件
- 模板字段说明文档
- 导入接口或导入按钮
- 导入校验与错误报告

建议实现：

1. 模板说明文档统一放在 `docs/`；`xlsx` 模板文件本体放在 `templates/`
2. 配置页“认证与用户”增加“下载模板”和“导入用户”入口
3. 服务端接收 `xlsx` 文件后完成解析、校验、去重、角色整理、密码哈希
4. 阶段一先写入 `auth.builtinUsers` 和 `auth.roles`，作为后续迁移到 `SQLite` 的过渡基线

导入校验至少包括：

- 用户名不能为空
- 用户名不能重复
- 初始密码不能为空
- 角色名去空格、去重
- 不允许导入保留冲突用户名

密码处理要求：

- Excel 中填写明文初始密码
- 服务端按现有规则生成哈希
- 使用当前 `passwordSalt` 规则
- 不在响应或日志中回显明文密码

### 阶段二：builtin SQLite 化

目标：把本地兜底账号从配置文件迁移到 `SQLite`，为后续长期维护做收口。

建议实现：

1. 新增 `builtin` 用户仓储层，支持 `SQLite`
2. 将用户、角色和用户角色关系从 YAML 结构迁移到表结构
3. 配置文件中不再长期保存大量本地用户，仅保留数据库路径、认证方式和必要开关
4. `xlsx` 导入最终写入 `SQLite`
5. 预留导入记录、禁用状态、最近登录时间等扩展字段

建议最小表结构：

- `builtin_users`
- `builtin_roles`
- `builtin_user_roles`

可后续扩展：

- `builtin_import_jobs`
- `builtin_login_audits`

特别说明：

该阶段的目标不是把系统做成重数据库架构，而是把 `builtin` 从“配置文件中的账号列表”收敛为“本地轻量持久化存储”。

### 阶段三：IDaaS 接入设计落地

目标：把 OIDC 配置、回调链路和 JWT 颁发打通。

建议后端新增：

- `/api/auth/oidc/login`
- `/api/auth/oidc/callback`
- `/api/auth/oidc/logout`（可选）

建议配置项在现有 `oidc` 基础上扩展：

| 字段 | 用途 |
| --- | --- |
| `issuerURL` | OIDC Provider 地址 |
| `clientId` | 客户端 ID |
| `clientSecret` | 客户端 Secret |
| `redirectURL` | 回调地址 |
| `scopes` | 默认 `openid profile email` |
| `usernameClaim` | 用户名 claim |
| `emailClaim` | 邮箱 claim，建议新增 |
| `displayNameClaim` | 显示名 claim，建议新增 |
| `groupsClaim` | 用户组 claim，建议新增 |
| `defaultRoles` | 未匹配到映射时赋予的默认角色，建议新增 |
| `roleMappings` | IDaaS 组或角色到系统角色的映射，建议新增 |

角色映射建议优先采用：

1. `groups` / `roles` claim 映射
2. 找不到映射时使用默认角色
3. 特定本地管理员仍保留 `builtin`

### 阶段四：登录页与配置页改造

目标：让前端真正支持“本地登录 + 单点登录”并存。

建议策略：

- 若 `methods = [builtin]`：只展示账号密码登录
- 若 `methods = [oidc]`：只展示“使用 IDaaS 登录”
- 若 `methods = [builtin, oidc]`：同时展示两种方式

配置页建议增加：

- OIDC 配置区块
- 角色映射配置区块
- 导入用户入口
- 下载模板入口

### 阶段五：初始化与运维收口

目标：让系统在 OIDC 模式下可正确初始化和运维。

需要同步调整：

1. `setup-status` 判断逻辑
2. 登录页“未配置完成”的提示逻辑
3. 配置校验与错误提示
4. 管理员应急登录指引

特别说明：

当主认证方式为 `oidc` 时，系统不应再强制要求“存在至少一个本地用户”才算配置完成。

### 阶段六：AI 幻觉抑制收口

目标：让系统在缺少依据时不乱答，在有依据时能说明依据来自哪里。

建议实现：

1. 为问答链路补充来源元数据和命中状态
2. 系统提示词中明确禁止编造用户、权限、资源、日志结论和配置项
3. 检索为空或证据不足时，统一降级为“未找到足够依据，请补充范围或数据源”
4. 对权限、配置、运维操作、审计结论类问题，默认附来源说明或显式标记为推断
5. 前端补充“回答依据 / 依据不足”展示
6. 记录审计日志，便于回看问题、召回情况和最终回答

完成标志：

- 无依据时不输出确定性结论
- 高风险回答可以区分“事实”“推断”“建议”
- 幻觉问题可以被记录、复盘和迭代

## 7. 关键设计决策

### 7.1 builtin 的定位

`builtin` 不再作为长期主认证方式，而是：

- 首次部署初始化账号
- 应急管理员登录
- OIDC 异常时的兜底入口

### 7.2 JWT 的定位

项目应继续保留自己的 JWT，而不是直接把 IDaaS token 当作业务 token 使用。

这样做的原因：

- 现有业务接口和中间件都依赖项目自己的 JWT
- 项目可以对外部身份源保持解耦
- 后续如果接入多个身份源，业务层不需要大改

### 7.3 角色来源

推荐逐步从“本地用户绑定角色”迁移到“IDaaS claim 映射角色”。

本地角色配置仍保留，但用途逐步收敛为：

- builtin 用户授权
- OIDC 角色映射规则配置

### 7.4 用户存储方案选择

围绕“是否引入 SQLite 存储用户信息”，当前有三种可选方案：

#### 方案 A：`OIDC + 少量 YAML builtin`

定义：

- `IDaaS / OIDC` 作为主认证源
- `builtin` 仅保留少量本地管理员账号
- 本地账号继续保存在 `config.yaml` 的 `auth.builtinUsers / auth.roles`

优点：

- 与当前代码结构最接近，改动面最小
- 可以最快把 OIDC 主链路打通
- 不需要额外引入数据库初始化、迁移、备份和运维成本

缺点：

- 本地用户数量一旦增多，配置文件会变得难维护
- 不适合承载复杂的本地用户状态，例如禁用、备注、审计、最近登录时间

适用场景：

- 主体用户全部走 OIDC
- `builtin` 只保留 1 到 2 个应急管理员
- 当前阶段目标是尽快完成接入，而不是建设长期本地用户系统

#### 方案 B：`OIDC + SQLite builtin`

定义：

- `IDaaS / OIDC` 仍作为主认证源
- `builtin` 本地账号迁移到 SQLite 存储
- 配置文件只保留 OIDC 配置、JWT 配置和必要的系统参数

优点：

- 本地用户、角色、审计信息更容易扩展
- 比 YAML 更适合做批量导入、状态管理和后续后台维护
- 如果后续要加导入记录、最近登录时间、禁用状态，会更自然

缺点：

- 会额外引入数据库文件、初始化、迁移和备份问题
- 当前项目还没有数据库基线，这会把阶段二的复杂度明显抬高
- OIDC 本身并不依赖 SQLite，因此这部分建设容易和主线耦合过早

适用场景：

- 虽然主认证是 OIDC，但仍然计划长期维护较多本地账号
- 后续明确要做本地用户后台、审计和状态管理

#### 方案 C：`纯 OIDC，无本地用户`

定义：

- 系统完全依赖 `IDaaS / OIDC`
- 不再保留 `builtin` 本地账号

优点：

- 认证模型最简单，长期维护成本最低
- 不需要本地密码体系和本地用户导入能力

缺点：

- OIDC 或 IDaaS 配置异常时，没有应急登录入口
- 首次部署、故障排障和高风险变更时缺少兜底手段

适用场景：

- 平台对 IDaaS 可用性有很强信心
- 已经有成熟的企业级身份运维流程
- 可以接受没有本地 break-glass 账号

#### 当前建议

当前阶段建议采用 **方案 B：`OIDC + SQLite builtin`**。

原因：

- OIDC 本身不依赖 SQLite，但 `builtin` 作为长期兜底能力，放在配置文件里可维护性偏差
- `SQLite` 能承接批量导入、角色关系、审计字段和后续本地用户状态扩展
- 相比引入 MySQL / Postgres，`SQLite` 对当前项目的运维成本更低，更适合作为本地轻量存储层
- 这样可以把“主认证走 OIDC”和“本地兜底账号可长期维护”同时兼顾

建议执行顺序：

1. 保留当前已完成的 YAML 导入能力作为过渡基线
2. 尽快把 `builtin` 存储迁移到 `SQLite`
3. 在 `SQLite builtin` 基础上完成 OIDC 主链路
4. 最终形成“OIDC 主认证 + SQLite builtin 兜底”的结构

### 7.5 AI 幻觉抑制原则

AI 幻觉抑制优先依赖“依据约束 + 输出约束 + 前端提示”，而不是仅靠模型自觉。

原则如下：

- 能引用依据时再给确定性答案
- 不能确认时明确说不能确认
- 高风险场景宁可保守，也不要补全细节
- 事实、推断、建议尽量分开表达

## 8. 风险与注意事项

### 8.1 用户导入风险

- Excel 模板字段膨胀会导致期望与系统能力不一致
- 密码导入若在前端做哈希，安全和一致性都不好
- 导入后角色覆盖规则若不清晰，容易误删已有授权

建议：

- 第一版仅支持“追加导入”或“按用户名覆盖”
- 明确导入模式，不做隐式合并

### 8.2 OIDC 接入风险

- 回调地址配置错误会直接导致无法登录
- `state` / `nonce` 校验不完整会带来安全风险
- 角色 claim 不稳定会导致权限结果不可预测
- 登出逻辑如果只清本地、不退出 IDaaS，会让用户误解

建议：

- 第一版优先完成登录链路
- 单点登出作为后续增强项

### 8.3 初始化判断风险

当前登录页未完成判断依赖“本地用户存在”，后续若不改，会导致：

- OIDC 已配置成功
- 但前端仍提示“尚未创建任何登录用户”
- 造成错误认知和部署障碍

### 8.4 AI 幻觉抑制风险

- 如果只改 Prompt，不改检索和前端提示，用户仍会把推断当事实
- 如果没有来源展示，回答即使基于证据，用户也无法判断可信度
- 如果未命中时仍强行组织完整答案，会持续放大错误认知

建议：

- 高风险回答优先做来源展示
- 未命中时优先返回澄清或降级提示
- 把幻觉样本纳入后续回归和评审

## 9. 推荐实施顺序

建议按以下顺序推进：

1. 先做 `xlsx` 模板设计
2. 再做 `builtin` 用户导入
3. 再做 `builtin` 存储 SQLite 化
4. 同步补一份 `OIDC / IDaaS` 接入设计
5. 再实现后端 OIDC Provider
6. 改前端登录页与配置页
7. 最后补 AI 幻觉抑制规则、前端提示和审计闭环

## 10. 本轮建议结论

当前建议采用如下决策：

1. `xlsx` 导入：做，但仅服务于 `builtin`
2. `IDaaS`：作为主认证方案推进
3. `builtin`：只保留少量管理员兜底账号
4. `OIDC`：优先于 `LDAP`
5. 用户存储：目标方案采用 `OIDC + SQLite builtin`
6. AI 幻觉抑制：作为总体目标之一同步推进，不再视为后置优化项
